## 5. Threats to validity

- **Circularity of O4.** The interpreter shares the lexer, parser and data layout with Phase 0, so E5 can only find errors in Phase 0's read/write *analysis*, not in the shared front end. E5 is labelled model-based and every claim it supports is also backed by an independent oracle: layout by O1 (E3), control flow by O2 (E4).
- **Small, synthetic corpus.** D1 and D2 are 38 short programs written to exercise semantics; they lack the size and idioms of production code. D3 (CardDemo) adds scale but no ground truth beyond coverage and hazard counts.
- **GnuCOBOL is the reference, not IBM Enterprise COBOL.** Sizes, DISPLAY formats and trace semantics are GnuCOBOL 3.2 `-std=default`; IBM-specific behaviour (and CICS/IMS/DB2 programs, which fall back to the tolerant analyser) is outside what the oracles can confirm.
- **Annotator bias (E6).** The two annotators are project members who know COBOL and the guide's definitions; agreement is reported to bound this. The guide was written from the same definitions Phase 0 implements, so a shared misreading of COBOL would not be caught.
- **Permissive E4 rule.** Traces do not show PERFORM returns, so a transition is accepted when an earlier performer has a static edge to the target; a full call-stack model would be stricter.
- **Random states in E5.** Values are valid for each PIC; invalid data (e.g. an X(n) REDEFINES of a numeric item) is not perturbed, and paragraphs whose runs need open files are refused (counted in `refused_runs`).
