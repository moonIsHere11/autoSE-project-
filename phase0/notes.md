## M1: skeleton, contract, inventory

- Layout: `phase0/phase0/` package, `phase0/bin/phase0` wrapper (same pattern as `phase2/bin/phase2`: re-exec under the verifier venv with the repo root on `PYTHONPATH`). Separate `phase0/pyproject.toml` only for mypy (`mypy_path = ".."` so the editable `verifier` install resolves); ruff uses the root config. Makefile `lint` and `typecheck` now include phase0.
- Schemas (`schema.py`): pydantic models with `extra="forbid"` for everything Phase 0 writes; 1.1 additions are optional with defaults, so 1.0 readers are unaffected. `Field` is `Field_` in Python only (name clash with pydantic). Confidence is a float in [0, 1] (strict = 1.0, tolerant lower) so coverage can sum it.

- Tool config: Phase 0 uses `VerifierConfig()` defaults, because Phase 2's adapter calls `verifier.api.verify` without a config, so `-std=default` regardless of `config.yaml`'s `dialect`. Recorded the mismatch risk (config says `ibm` in the agreement example) for TEAM_NOTES.
- Inventory (stage A): classification by content (JCL cards, BMS macros, PROGRAM-ID + PROCEDURE DIVISION in the code area, level-number lines for copybooks), never by extension. ## M2-M3: parse, layout, control flow, data flow, hazards, coverage

- Stage B (`stages/parse.py`): `preprocess_all` (cobc -E in the toolchain image, cached under `W/.phase0-cache`) -> `tokenize` -> `parse_source` -> `lower_program` (typed IR). Programs are chosen by inventory classification (content), not by suffix. Result on D1+D2: all 38 programs parse strictly (14 corpus programs = 101 paragraphs, matching the task statement; 24 semantics programs, not 25).
- Stage C (`stages/layout.py`): field ids are qualified paths from level 01/77, `PROG.` prefix only for multi-program workspaces (Phase 1's convention). FILLERs get `FILLER#k` so every byte has an entry, but they are excluded from unit reads/writes (no program can name them). `byte_length` is ONE occurrence (`unit_size`), `offset` is the first occurrence relative to the 01 record; `occurs` gives the count. `semantic_type` maps datadiv's PicInfo: numeric -> decimal(digits, scale, signed); everything else elementary -> alphanumeric(length); groups -> group(unit_size). RETURN-CODE is added as a field only when a unit touches it.
- Storage model (`stages/storage.py`): one rule replaces separate group-expansion and REDEFINES logic: a reference touches every elementary item whose bytes overlap its bytes, over all OCCURS occurrences, within one storage area (a 01 and its REDEFINES chain; all records of an FD). Chose byte overlap over `analysis.item_aliases` because item_aliases works on names (ambiguous across records) and returns groups and ancestors, not elementary items.
- Stage E (`stages/dataflow.py`): effects from the IR (same name resolution as the checker). Definitions (also for the gold guide): reads = elementary items whose value at entry may be used; writes = items some statement may store into. A write that does not cover the whole item (subscripted, reference-modified, OCCURS element, partial overlap) also counts as a read, because the bytes it does not write pass through. Statements the IR does not lower (INSPECT, FUNCTION calls) fall back to the syntax tree with every operand read (over-approximation, confidence 0.8 on that unit); CALL/EXEC operands are treated as written too.
- **Fix found while checking PAYROLL output:** READ first counted as a partial write of the record (so every record field was also a read). A successful READ replaces the whole record and a failed one leaves it untouched, so neither depends on the old value; changed to a full write.
- Stage D (`stages/control.py`): from the syntax tree (complete where the IR gives up). `performs` = named targets, THRU ranges expanded to every paragraph, a section named as itself; `perform_thru` keeps the (first, last) pairs. Fall-through unless the last top-level statement always leaves (STOP RUN, GOBACK, EXIT PROGRAM, GO TO without DEPENDING). Dynamic CALL resolved when every store into the item (VALUE + MOVEs) is a literal. ALTER and partially overlapping THRU ranges become hazards.
- Units: one `program` unit (id = PROGRAM-ID) + sections (span = header to end of last paragraph, facts = union of its paragraphs) + paragraphs. A paragraph the verifier synthesises for a section's leading sentences (same name as the section) is merged into the section unit.
- **Verifier bug found (TEAM_NOTES 5):** `parser.py` leaves `Paragraph.end_line` at the header line when a SECTION header follows the paragraph (FALLTHRU: P-EXIT 26-26 instead of 26-31, S2-B 36-36). Found because coverage reported 6 unexplained lines in FALLTHRU. Phase 0 computes paragraph ends from the token stream instead; after the fix D1+D2 have 0 unattributed lines (3256 lines: 3001 attributed, 249 comment, 6 now attributed).
- Stage F (`stages/hazards.py`): Phase 1's rules ported 1:1 onto IR statements (same gap ids, messages, severities); arithmetic inside IR-unsupported statements is scanned on the syntax tree. Unit-level G-GOTO / G-FALLTHROUGH / G-PACKED as in Phase 1.
- Coverage (`stages/coverage.py`): token regions (identification/environment = structure; data = inside an entry/FD/header; procedure = inside a unit span or header). Lines without tokens: COPY statements (attributed), compiler directives and preprocessor-dropped text (listed with reason).
- Tolerant fallback (`stages/tolerant.py`): Phase 1's analyser per rejected file, tagged `tolerant`, confidence 0.6; field types still come from `datadiv.parse_pic` (same PICTURE semantics), but no layout facts. Only known failure modes of the regex analyser are caught (ValueError, KeyError, ...); anything else propagates.

## CardDemo (D3) first build: robustness fixes

- Cloned `aws-samples/aws-mainframe-modernization-carddemo` (depth 1) into `data/carddemo` (gitignored), since no copy was on disk; the whole `app/` tree (240 files, 61,802 lines) is the D3 source. Build time 2.5 s.
- **Fix: copybook directories.** First build: 26 of 44 programs rejected by `cobc -E`, many only because BMS copybooks live in `cpy-bms/`, which the verifier's default `copy_dirs` (`copy, copybooks, cpy, copylib`) does not search. Phase 0 now appends the directories that hold copybooks (by content) AFTER the verifier's own dirs. Earlier `-I` wins, so any program the verifier can preprocess resolves every COPY exactly as before (principle 2 holds); the remaining rejections are IBM-supplied copybooks that are not in the repo (DFHAID, DFHBMSCA, CMQ*) or embedded-SQL syntax, which is the honest answer. (Still 18 strict / 26 tolerant: the cpy-bms programs now fail on DFHAID instead.)
- **Fix: inventory.** `README.md` and `.dcl` files were classified as procedure copybooks (the rule "any COBOL verb + ends with a period" matches prose). Now a procedure copybook needs a paragraph header and at least a third of its code lines to be statements; `EXEC SQL DECLARE` files are `copybook/sql`; data copybooks need half their code lines to be level entries.
- **Fix: coverage reasons.** AUTHOR/DATE-WRITTEN comment entries and `==x== BY ==y==` REPLACING continuation lines (dropped by cobc -E) are now attributed as structure. Reasons now depend on parse status ("copybook not included by any parsed program", "tolerant analyser dropped the line", ...). Tolerant files get the same structural attribution as strict ones (identification/environment text, headers, FD/88/66 entries, FILLER entries).
- Result: D3 unattributed lines 5,621 -> 510 of 39,670 program/copybook lines, every one with a reason: 253 data-division text after a strict parser error (verifier `datadiv` rejects e.g. `PIC X OCCURS ... of` constructs in CBSTM03A, CSUTLDTC; recorded in `parse_errors`), 165 lines of copybooks no program includes, 73 tolerant-file lines (EXEC SQL blocks in the data division), 19 dropped continuation/debug lines.

## Evaluation harness: O1 / E3 (data dictionary)

- `phase0/phase0/evaluation/` holds the harness (package code, so `phase0 eval` can run it); `phase0/eval/` holds data (gold, results).
- O1 has two parts. Listing: `cobc -fsyntax-only -t LIST -ftsymbols -fno-ttimestamp` prints SIZE, TYPE, LEVEL, NAME, PICTURE, OCCURS, REDEFINES per item (checked that cobc 3.2 in the image supports it). Probe: the `layout_probe.py` named in `datadiv.py`'s docstring does not exist in the repo, so Phase 0 generates its own: original program up to PROCEDURE DIVISION, probe items inserted after the WORKING-STORAGE header, and a procedure that prints, per item, the pointer difference to its 01 record (`USAGE POINTER` redefined as `S9(18) COMP-5`), `FUNCTION BYTE-LENGTH`, and the DISPLAY of `MOVE -1` (sign present, digit count, decimals). Items are addressed with full `OF` qualification and `(1, ...)` subscripts; numbers are keys, not field ids, to keep literals short. The KB only supplies the names to ask about; every number comes from GnuCOBOL.
- Listing items and KB fields are aligned on (level, name) in document order with difflib, so a missing or extra item shows up as `kb_only` / `listing_only` (field inventory check).
- First E3 run: 33 mismatches, all scorer issues, fixed in the scorer (the KB was right in every case): (1) the listing's TYPE is the item's class, so numeric-edited items are `NUMERIC` there while datadiv/the contract treat them as character storage; compare the KB `category` instead (27 items); (2) the corpus manifests use `kind: binary` for COMP items (4); (3) `PACKED-DECIMAL` is `COMP-3` (1); (4) GnuCOBOL DISPLAYs the P positions of `PP9(2)`, so digit counts are not observable for P pictures (1, excluded with that reason).
- Result D1+D2: every attribute 100% (listing: 710 items aligned, 0 KB-only, 0 listing-only; probe: 650 offsets and byte lengths, 388 numeric sign/digits/scale; manifests: 44 declared numeric types, 8 lengths).
- Speed: tool versions were read twice per build (two docker runs); cached per process. D1+D2 build (38 programs x 2 builds) 33 s -> 7.5 s.
