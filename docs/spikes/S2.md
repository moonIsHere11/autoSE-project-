# Spike S2 — JBMC 6.8.0 as the Java T2b equivalence checker

Time box: ~2 h. Sources, scripts and raw logs live in `docs/spikes/s2/` (logs in `docs/spikes/s2/out/`).
Everything quoted below was run inside `cobol-verifier-toolchain:0.1.0` on this machine (16 cores,
WSL2 VM with 7.6 GB RAM + 2 GB swap). Several runs were done in parallel, so wall times carry a
note on load.

## 1. Goal

Find out whether JBMC can prove unit-level equivalence of a trusted "reference" Java translation
and an LLM's Java translation of a COBOL paragraph (tier T2b): nondet inputs restricted to PIC
domains, both units run on identical state, assert all fields equal. Specifically:

* class-file compatibility with javac 17;
* the exact command line;
* machine-parsable outcomes;
* counterexample extraction and concrete replay;
* vacuity detection;
* cost;
* gotchas.

`nondetWithNull/WithoutNull(T)` and `assume(boolean)`. It has **no** `assert`. Properties come from
plain Java `assert` statements (§6.3).

## 3. Spike code (`docs/spikes/s2/src/s2/`)

| File | Role |
|---|---|
| `Dec.java` | Toy long-backed COBOL decimal: `long unscaled; int digits; int scale; boolean signed`. Provides `pow10` (a `switch`, so no array or loop), `rescale` (truncate, or ROUNDED = half away from zero), and `store`, which aligns the scale, truncates high-order digits (`% 10^digits`, keeping the sign) and takes the absolute value for unsigned fields. It also has `add / subtract / multiply / divide`. |
| `RefUnit.java` | Reference for `CALC-TOTAL`: `ADD WS-A TO WS-B GIVING WS-C ROUNDED` and `SUBTRACT WS-B FROM WS-A GIVING WS-D`, with WS-A, WS-B `S9(5)V99`, WS-C `S9(5)V9` and WS-D `9(4)V99`. |
| `LlmGood.java` | A correct "LLM" translation written differently: plain scaled `long` fields, `(mag+5)/10` rounding, abs before modulo. |
| `LlmBug.java` | Buggy: ROUNDED is implemented as truncation (`sum / 10`). |
| `LlmBugTrunc.java` | Buggy: forgets the high-order truncation of WS-D (`9(4)V99`). |
| `Harness.java` | T2b harnesses: `checkGood`, `checkBug`, `checkBugTrunc`, the reachability probe `reachGood`, and `contradictoryBug` / `contradictoryReach`. |
| `Cost.java` | Cost probes: `mulRescale(+Bug)` (`COMPUTE P ROUNDED = A * R`), `divRounded` (`COMPUTE Q ROUNDED = A / B`), and `loopSum5/10` (OCCURS 5/10 with `PERFORM VARYING`). |
| `Gotchas.java` | Probes for exceptions, null inputs, `Math.abs`, `BigDecimal`, and PIC X through `char[]`, `String` or `StringBuilder`. |
| `Replay.java` | Concrete replay with plain `java`, without CProver. |

Harness shape (from `Harness.java`):

```java
static long pic(int digits, boolean signed) {          // nondet value in a PIC domain
    long v = CProver.nondetLong();
    long lim = Dec.pow10(digits);
    CProver.assume(v < lim);
    CProver.assume(signed ? v > -lim : v >= 0);
    return v;
}
public static void checkBug() {
    long in_wsA = pic(7, true);  long in_wsB = pic(7, true);   // S9(5)V99
    long in_wsC = pic(6, true);  long in_wsD = pic(6, false);  // S9(5)V9, 9(4)V99
    RefUnit r = ref(in_wsA, in_wsB, in_wsC, in_wsD);
    LlmBug l = new LlmBug(); l.wsA = in_wsA; l.wsB = in_wsB; l.wsC = in_wsC; l.wsD = in_wsD;
    r.calcTotal();
    l.calcTotal();
    assert r.wsA.unscaled == l.wsA : "EQ WS-A";   // one assert per field
    assert r.wsB.unscaled == l.wsB : "EQ WS-B";
    assert r.wsC.unscaled == l.wsC : "EQ WS-C";
    assert r.wsD.unscaled == l.wsD : "EQ WS-D";
}
```

## 4. Commands (copy-pasteable)

From the repo root in WSL, each experiment runs as `bash docs/spikes/s2/run.sh <script>`.
`run.sh` does `docker run --rm -m 5g --memory-swap 5g -v $PWD/docs/spikes/s2:/w -w /w cobol-verifier-toolchain:0.1.0 bash /w/<script>.sh`.

| Script | What it does |
|---|---|
| `e1_versions` | Class-file versions 61, 55 and 52 with default options |
| `e2_outputs` | Outcome classes in JSON, XML and text, vacuity, tool errors |
| `e2b_parse_replay` | `parse_jbmc.py` on every E2 JSON, then concrete replay |
| `e3_solvers`, `e3b_solvers` | Solver and option sweep on the add/sub proof |
| `e4_cost cadical --sat-solver cadical` | Cost table |
| `e5_gotchas`, `e5b_strings`, `e6_flags` | Gotchas |

The core commands, run inside the container from `/w`:

```bash
javac -g -cp /usr/lib/cprover-api.jar -d build/r17 src/s2/*.java          # plain javac 17, no --release

jbmc s2.Harness --function s2.Harness.checkGood \
     -cp build/r17:/usr/lib/cprover-api.jar \
     --unwind 5 --unwinding-assertions --sat-solver cadical \
     --json-ui --trace > out.json; echo "exit=$?"

python3 parse_jbmc.py out.json <exit-code>                                 # verdict + inputs
java -cp build/r17 s2.Replay Bug -3 -2 -1 0                                # concrete replay
```

* **Entry point.** Give the class as the positional argument and select the method with
  `--function <pkg>.<Class>.<method>`. All three of these forms worked (`e7_cli`):
  * `--function s2.Harness.checkGood`;
  * the descriptor form `--function 's2.Gotchas.divZero:(JJ)J'`, which overloaded methods need;
  * the method as the positional argument, `jbmc -cp ... 's2.Gotchas.divZero:(JJ)J'`.
* **Classpath.** Use `-cp <classes>:/usr/lib/cprover-api.jar`.
  * javac needs the jar.
  * jbmc intercepts `CProver.nondet*`/`assume` internally. Without the jar on jbmc's `-cp`, the
    contradictory-assumption harness still gave `VERIFICATION SUCCESSFUL` (`e7_noapi_contra.txt`),
    so `assume` was still honoured. Keep the jar on `-cp` anyway, for consistency.
  * With no `-cp` at all, jbmc exits 6 ("Could not find or load main class").

## 5. Findings

### 5.1 Q1 — Java 17 class files: **accepted, no workaround needed**

`e1_versions` compiles the same sources three ways and runs `checkGood` with default options
(MiniSAT), one after another:

```
== release=default  class version:   major version: 61
e1_rdefault_checkGood.txt                rc=0   wall= 89.85s     ** 0 of 115 failed (1 iterations)  VERIFICATION SUCCESSFUL
== release=11  class version:   major version: 55
e1_r11_checkGood.txt                     rc=0   wall= 98.62s     ... VERIFICATION SUCCESSFUL
== release=8  class version:   major version: 52
e1_r8_checkGood.txt                      rc=0   wall= 97.59s     ... VERIFICATION SUCCESSFUL
```

The only warning in the log is the harmless `stub class symbol java::java.lang.Object already exists`.

**There is one real Java-9+ problem: `invokedynamic` string concatenation.** With `--release 17`,
`s + "        "` compiles to `makeConcatWithConstants`. JBMC treats its result as `null`, so it
reports `null-pointer-exception.2 ... FAILURE` at the following `.substring` (`e5_picXConcat_r17.txt`).
With `--release 8` the concatenation compiles to `StringBuilder` and the NPE goes away. Strings
still do not verify (§6.4).

**Recommendation:** compile harness, reference and candidate with `javac --release 8`. It costs
nothing: timings were similar to release 17 (97.6 s vs 89.9 s, within run-to-run noise), and it
removes indy string concat. Lambdas
and records are also indy- or Java-16-based and were not tested. Treat them as T2b `NOT_APPLICABLE`.

### 5.2 Q2 — Outcome classes and how to parse them

Use `--json-ui --trace`. The output is a JSON array:

* status messages: `{"messageType":"STATUS-MESSAGE",...}`;
* errors: `{"messageType":"ERROR","messageText":...}`;
* one `{"result":[...]}` object with one entry per property: `property`, `description`, `status`,
  `sourceLocation{file,line,function,propertyClass}`, and `trace` when the status is FAILURE;
* a final `{"cProverStatus":"success"|"failure"}`.

XML (`--xml-ui`) carries the same information: `<result property=... status=...>` and
`<assignment base_name="in_wsA" ...>`. JSON is easier to consume.

| Case | Exit code | `cProverStatus` | Failed property ids | Observed in |
|---|---|---|---|---|
| (a) all properties hold | **0** | `"success"` | none | `e2_checkGood.json`, 19.3 s |
| (b) assertion violated | **10** | `"failure"` | `java::s2.Harness.checkBug:()V.assertion.3`, line 62, `propertyClass:"assertion"` | `e2_checkBug.json`, 5.6 s |
| (c) unwinding bound too small | **10** | `"failure"` | `java::s2.Cost.loopSum:(I)V.unwind.0`, description `"unwinding assertion loop 0"` | `e2_loop5_unwind3.json` (loop of 5, `--unwind 3`) |
| (d) tool error: unknown class, no `-cp`, unknown `--function` | **6** | absent | `messageType:"ERROR"`, e.g. `"Error: Could not find or load main class s2.NoSuchClass"`, `"main symbol resolution failed: 's2.Harness.noSuchMethod' not found"` | `e2_err_*.json` |
| (d) unknown option | **64** | absent | stdout holds "Usage error!" plus help text, so the JSON does not parse | `e2_err_badopt.json`, `e6_flags` |
| (d) internal crash | **134** (SIGABRT) | absent | `--- begin invariant violation report ---` | `e3b_add_z3_norefstr.txt` |
| (d) out of memory / timeout | **137** / **124** | absent | killed | `e5b_picXConcat_r8_trace.txt`, `e5b_picXBuilder_trace.txt` |

The parsing rules are implemented in `docs/spikes/s2/parse_jbmc.py`:

1. If the exit code is not 0 or 10, the JSON does not parse, or `cProverStatus` is missing, the
   verdict is **TOOL_ERROR**. Keep the `messageType=="ERROR"` texts.
2. Otherwise collect the `result[]` entries with `status=="FAILURE"`.
   * If none failed and the exit code is 0, the verdict is **PROVED**. It still needs the vacuity
     check in §5.4.
   * If any failure has an id that does not contain `.unwind.`, the verdict is **COUNTEREXAMPLE**.
     It is an equivalence violation when the id contains `.assertion.`, and a runtime exception
     when it contains `null-pointer-exception`, `integer-divide-by-zero`, `array-index-out-of-bounds-*`,
     `array-create-negative-size` or `<fn>.N` with "no uncaught exception".
   * If only `.unwind.` properties failed, the verdict is **BOUND_INSUFFICIENT**: raise `--unwind`
     or report INCONCLUSIVE.
3. To map a failing assertion back to a COBOL field, use `sourceLocation.line`. The `assert`
   message string does **not** appear in the property description, so the harness generator has to
   keep a line-to-field map. The alternative is the ordinal in `....assertion.N`, which follows the
   order of the asserts in the source.

`parse_jbmc.py` output on the E2 runs (`out/e2b_parse_replay.txt`):

```

                                     inputs: {'in_wsA': -3, 'in_wsB': -2, 'in_wsC': -1, 'in_wsD': 0}
```

### 5.3 Q3 — Toy decimal: correct pair proves, buggy pairs give counterexamples, replay reproduces them

* **`checkGood` (reference vs `LlmGood`) proves.** `** 0 of 115 failed`, `VERIFICATION SUCCESSFUL`,
  exit 0, in 16.2 s with CaDiCaL and nothing else running.
* **`checkBug` (ROUNDED implemented as truncation) fails.** JBMC reports
  `[java::s2.Harness.checkBug:()V.assertion.3] line 62 ... FAILURE` (the WS-C assert), `** 1 of 115 failed`, in about 5 s.
* **`checkBugTrunc` (no high-order truncation) fails** on `assertion.4` (WS-D) in about 16 s.

**Extracting the counterexample.** Inputs are read from the trace of the failing property. The
harness keeps one local per COBOL input field, named `in_<field>`. For each one, take the
**last** trace step with `stepType=="assignment"`, `lhs=="in_<field>"`, `hidden==false` **and a
`sourceLocation`**. JBMC first emits a declaration step for each local with a garbage value (`-1L`)
and no `sourceLocation`, and those steps must be skipped. Decode the value from
`value.binary`/`value.width` as two's complement. `value.data` is a Java literal such as `"-3L"`, so
`Long.parseLong` rejects it. That actually happened on the first replay attempt
(`NumberFormatException: For input string: "-3L"`).

Example step from `e2_checkBug.json`:

```json
{ "lhs": "in_wsA", "stepType": "assignment", "hidden": false,
  "sourceLocation": {"file": "s2/Harness.java", "function": "java::s2.Harness.checkBug:()V", "line": "51"},
  "value": {"binary": "1111...11111101", "data": "-3L", "name": "integer", "type": "long", "width": 64} }
```

**Concrete replay with plain `java`** (no CProver jar on the classpath, `out/e2b_parse_replay.txt`):

```
### replay Bug with: -3 -2 -1 0                  # WS-A=-0.03, WS-B=-0.02 -> sum -0.05
WS-C: reference=-1 candidate=0  MISMATCH         # ROUNDED -> -0.1 ; truncation -> 0.0
exit=1
### replay Good with: -3 -2 -1 0
WS-C: reference=-1 candidate=-1  ok              exit=0
### replay BugTrunc with: -294912 8388608 -1 0   # WS-A - WS-B = -86835.20
WS-D: reference=683520 candidate=8683520  MISMATCH   # 9(4)V99 keeps 6835.20
exit=1
### replay Good with: -294912 8388608 -1 0       ... all ok, exit=0
```

Both bugs reproduce concretely, and the correct candidate agrees on the same inputs. The
counterexamples are real and minimal-looking: JBMC found the half-way case -0.05.

### 5.4 Q4 — Vacuity

| Harness | Expected | Observed |
|---|---|---|
| `reachGood`: `checkGood` followed by `assert false : "REACH"` | FAILED, so the end is reachable | exit 10, `reachGood:()V.assertion.1` line 95 **FAILURE**, witness inputs all 0, 1.4 s |
| `contradictoryBug`: `assume(a>5); assume(a<3)` with the **buggy** candidate | vacuous pass | exit 0, `cProverStatus:"success"`, **PROVED although the candidate is buggy**, 0.45 s |
| `contradictoryReach`: same assumptions followed by `assert false` | vacuity detected | exit 0, `"success"`. The REACH assert is *not* violated, so the end is unreachable. |

The reachability probe is mandatory. A T2b PASS requires two runs: the equivalence run gives
PROVED, **and** the reach run (same harness, `assert false` after both calls) gives
COUNTEREXAMPLE on the REACH assert. If the reach run is PROVED, report "vacuous: assumptions
unsatisfiable or code unreachable" as T2b ERROR. The reach run is cheap (1.4 s here) because SAT
finds a witness quickly.

## 6. Gotchas (Q6)

### 6.1 Implicit exceptions are checked by default and reported as properties

* **Division by zero** (`e5_divZero.txt`, entry `divZero(long x, long y)`):
  `[java::s2.Gotchas.divZero:(JJ)J.integer-divide-by-zero.1] line 11 Denominator should be nonzero: FAILURE`.
  The trace shows `x=0L`, `y=0L`.
* **Array index out of bounds** (`e5_arrIdx.txt`):
  `...arrIdx:(I)J.array-index-out-of-bounds-high.1] line 17 Array index should be < length: FAILURE`
  and `...-low.1 ... >= 0: FAILURE`, with `i=6`.
* **Explicit uncaught `throw`** (`e5_explicitThrow.txt`):
  `[java::s2.Gotchas.explicitThrow:(I)V.1] line 27 no uncaught exception: FAILURE`.
  `--disable-uncaught-exception-check` turns this off.
* **`--throw-runtime-exceptions`** turns implicit checks into real exceptions. The single reported
  property is then `divZero:(JJ)J.1 ... no uncaught exception: FAILURE`.
* **Null-pointer checks** are emitted for every dereference: dozens of
  `Null pointer check: SUCCESS` lines among the 115 properties of the add harness. On objects the harness
  allocates itself they are trivially discharged.
* **CBMC check flags are not accepted.** `--no-built-in-assertions`, `--no-standard-checks`,
  `--div-by-zero-check` and `--no-div-by-zero-check` all end with `Usage error!` and exit 64
  (`e6_flags`). In JBMC 6.8 the Java checks are always on.

For T2b this behaviour is useful: a candidate that throws where the reference does not, for
example a `/0` on an in-domain input, becomes a COUNTEREXAMPLE whose property class names the
exception.

### 6.2 `--java-assume-inputs-non-null`

* Reference-typed **parameters of the entry method** may be null by default. `nullIn(Dec d)` gives
  `null-pointer-exception.1 ... FAILURE`. With `--java-assume-inputs-non-null` the result is
  `VERIFICATION SUCCESSFUL` (`e5_nullIn*.txt`).
* Our harness entry methods take **no parameters**: all nondet comes from `CProver.nondet*` and
  the objects are built with `new`. So the flag is irrelevant there. It is harmless, so pass it anyway.
* `--max-nondet-array-length` only bounds nondet arrays that JBMC synthesises for entry parameters.
  Not used.

### 6.3 Java `assert` statements are properties

Each `assert` becomes property `<fn>.assertion.N` with the description
`"assertion at file F line L function ... bytecode-index B"`. No `-ea` is involved, because JBMC
does not run a JVM; its trace initialises `$assertionsDisabled=false` (`e5_mathAbs.txt`). The assert *message* is not part of the description
(§5.2). `--no-assertions` would disable them, so never pass it.

### 6.4 JDK library calls are silently stubbed, which produces spurious counterexamples

This is the biggest practical gotcha. JDK 17 has no `rt.jar`, so JBMC sees no bytecode for most
of the JDK. Every call to a method without a model becomes a stub that returns a nondet value and
has **no side effects**, and **no warning is printed**.

* **`Math.abs`** (`e5_mathAbs.txt`): the trace shows `java.lang.Math.abs()(0L)`, then `m=1009L`,
  then `assertion.1 ... FAILURE` for `assert m >= 0 && m < 1000`.
  * **Workaround tested:** extract the real class with
    `jimage extract --include 'regex:/java.base/java/lang/Math\.class' $JAVA_HOME/lib/modules` and
    add `build/jdkx/java.base` to `-cp`. The same harness then gives
    `** 0 of 16 failed ... VERIFICATION SUCCESSFUL` (`e5b_mathAbs_jdkMath.txt`).
    So a whitelist of pure JDK classes (`Math`, possibly `Long`/`Integer`) can be put on the
    classpath. **Each class has to be validated individually.**
* **`System.arraycopy`** (`e5b_picXCharArray_trace.txt`): the trace shows
  `java.lang.System.arraycopy()(...)` with no assignments inside, so the target `char[]` is
  unchanged and the run gives a spurious FAILURE. The same copy written as a loop
  (`picXCharArrayLoop`) gives `VERIFICATION SUCCESSFUL` in 0.6 s. The buggy loop variant (pads
  with `'0'`) gives FAILURE in 0.6 s.
* **`java.math.BigDecimal`** (`e5_bigDecimal.txt`): every call is a stub.
  `BigDecimal.add()(&dynamic_object$4, null)` receives null objects, and the run reports four
  `null-pointer-exception ... FAILURE` plus `assertion.1 ... FAILURE`. **A candidate written with
  BigDecimal, which is the usual LLM style, is not T2b-checkable.**

**Consequence for the verifier:**

* Every T2b COUNTEREXAMPLE must be confirmed by concrete replay (§5.3) before it is reported as
  FAIL. If the replay shows no mismatch, the verdict is INCONCLUSIVE ("unmodelled library call").
* Also pre-scan the candidate's bytecode with `javap -c` for `invokestatic`/`invokevirtual` into
  `java/`, other than `String`/`StringBuilder`/`Object` and the whitelist. If any are found, mark
  T2b `NOT_APPLICABLE`.
* Stubs leave arguments unchanged, so a stubbed mutator can also make a buggy candidate look
  equal. Example: an unmodelled `Arrays.fill` on a field that the reference also leaves unchanged
  in that path. This is another reason for the pre-scan.

### 6.5 String / char[] for PIC X: `char[]` is fine, `String`/`StringBuilder` is not acceptable

The case is `MOVE WS-IN (X(5)) TO WS-OUT (X(8))`. Nondet chars are assumed to be in `' '..'~'`.

| Candidate style | Result |
|---|---|
| `char[]` with an explicit loop | **SUCCESS** in 0.6 s. The buggy variant gives FAILURE in 0.6 s. |
| `char[]` with `System.arraycopy` | spurious FAILURE (stub, §6.4) |
| `String` concat, `--release 17` | spurious NPE FAILURE (indy concat yields null) |
| `String` concat, `--release 8` | FAILURE on `assert llm.length()==8`, on a null-pointer check and on the char compare, so a **correct** candidate is rejected. With `--trace` the run was OOM-killed (exit 137) while "Building error trace". |
| `StringBuilder` + `append` loop | FAILURE on length and char asserts for a **correct** candidate, also with `--string-printable --max-nondet-string-length 16`. With `--trace` and default options it ran until `timeout 600` and was finally killed after 1000 s (exit 124). It also pushed the WSL VM into swap thrash for about 15 min. |
| `StringBuilder` with a planted bug | FAILURE, but every String variant fails, so this result carries no information |

I did not root-cause *why* the String model rejects these correct candidates within the time box.
The verdict is practical: **with String code, T2b would produce spurious failures and memory
blow-ups.**

* Model PIC X as fixed-length `char[]` in the reference runtime.
* Make T2b `NOT_APPLICABLE` when the candidate uses `String`/`StringBuilder` on the unit's data path.
* Never run a String harness with `--trace` without a memory cap (`docker run -m`) and a hard
  `timeout -k`.

## 7. Cost (Q5)

Timings are wall time for the whole `jbmc` process, from `date +%s.%N` around the call. "Parallel"
means the run shared the 16-core VM with up to 6 other jbmc processes.

**Solver and option sweep on the add/subtract proof** (`checkGood`, 4 nondet `long` inputs, 4 field
asserts, 28,692 variables / 77–80 k clauses, UNSAT):

|---|---|---|
| default (MiniSAT 2.2.1, run alone) | **89.9 s** | `e1`, release 17. Release 11: 98.6 s; release 8: 97.6 s. |
| default MiniSAT (parallel ×6) | 149.0 s | `e3_add_minisat_default` |
| `--no-refine-strings` (MiniSAT with simplifier, parallel) | 92.5 s | `e3_add_norefstr` |
| `--no-refine-strings --no-sat-preprocessor` (parallel) | 148.6 s | |
| `--z3` | 149.2 s | **silently ignored**: the log still says "string refinement loop with MiniSAT 2.2.1" |
| `--no-refine-strings --z3` | crash, exit 134 | `Invariant check failed ... smt2_conv.cpp:5964 ... unsupported type: string` |
| **`--sat-solver cadical` (run alone)** | **16.2 s** | `e3b_add_cadical_solo`. Best result. |
| `--sat-solver cadical` (parallel) | 24.5 s | `e3_add_cadical` |

| `--sat-solver cadical --slice-formula` | 29.9 s | no gain |
| cadical, one process per `--property` | WS-A 0.35 s, WS-B 0.35 s, WS-D 7.8 s, WS-C 270.7 s | Splitting by property made WS-C, the ROUNDED add, much *slower* than proving all four together. That run overlapped the memory thrash, so the 270 s is not reliable, but there was no evidence of a gain. |

**Cost table with CaDiCaL** (`e4_cost cadical --sat-solver cadical`, 7 jobs in parallel; `--unwind 5`,
or N+1 for loops):

| Probe | COBOL | Result | Wall | SAT size |
|---|---|---|---|---|
| (a) add/sub, correct | `ADD … ROUNDED`, `SUBTRACT …` | PROVED | 33.4 s (16.2 s run alone) | 28.7 k vars / 80 k clauses |
| (a) add/sub, bug | ROUNDED replaced by truncation | CEX | 8.7 s | 27.7 k / 78 k |
| (b) multiply + rescale, correct | `COMPUTE P ROUNDED = A * R` (`S9(5)V99 × 9V9(4)`) | **TIMEOUT**, no verdict (`timeout 900`, exit 124) | > 900 s | 31.7 k / 132 k |
| (b) multiply + rescale, bug | truncation instead of rounding | CEX | 5.6 s | 30.8 k / 130 k |
| (b') general division, correct | `COMPUTE Q ROUNDED = A / B`, B ≠ 0 | **TIMEOUT**, no verdict (exit 124) | > 900 s | 46.8 k / 198 k |
| (c) OCCURS 5 loop, correct | `PERFORM VARYING I 1..5  ADD AMT(I) TO TOTAL` | PROVED | 31.8 s | 31.2 k / 99 k |
| (c) OCCURS 10 loop, correct | the same with 10 elements | PROVED | 87.1 s | 57.5 k / 185 k |

Takeaways:

* **Multiplication or division by a variable cannot be proved this way.** The run was stopped
  after 15 minutes of CaDiCaL with no verdict, for both the 64-bit `nondet × nondet` product
  followed by rescaling and the `nondet / nondet` quotient.
  * The reference and the candidate compute the same value through *different* arithmetic. That
    forces the SAT solver to prove the equivalence of two multiplier or divider circuits, which is
    a classic hard case for bit-blasting.
  * Counterexamples for the buggy multiply still arrive in 5.6 s.
  * I did not try case-splitting the domain, `int`-width variants, or structurally identical
    candidates, which would probably prove quickly because they hash to the same circuit. These
    are untested ideas.
* **Counterexamples are cheap** (about 5–9 s). **Proofs are expensive** and grow with every 64-bit
  `/` or `%`. Each COBOL store contains a `% 10^digits`, and each ROUNDED/rescale adds a `/ 10^k`.
  The formula is about 28 k variables for 2 statements. That is consistent with full 64-bit divider
  circuits even for constant divisors, but I did not inspect the CNF to confirm it.
* CaDiCaL is about 5× faster than the default MiniSAT on the add proof. **Always pass
  `--sat-solver cadical`.**
* The loop cost grows roughly linearly with OCCURS size: about 31 s for 5 elements and 87 s for
  10, under parallel load. The likely cause is the per-iteration `% 10^9` in the reference's
  `store`; I did not measure a variant without it.

## 8. Problems and workarounds

| Problem | Workaround |
|---|---|
| Default MiniSAT is slow on divider-heavy proofs (90 s for a 2-statement paragraph) | `--sat-solver cadical` (16 s) |
| Proofs of variable×variable multiply and variable÷variable divide time out (> 900 s) | None found within the time box. Use T2b as a bug finder for such units (INCONCLUSIVE on timeout); untested ideas are listed in §7. |
| `--z3`/`--smt2` are ignored, or crash with `--no-refine-strings` | Use the SAT back end only |
| Unmodelled JDK methods are silently stubbed, giving spurious CEX and possibly missed side effects | Concrete replay of every CEX; bytecode pre-scan; optional whitelist of real JDK classes extracted with `jimage` (tested with `Math`) |
| `invokedynamic` string concat yields null | `javac --release 8` |
| `String`/`StringBuilder` gives spurious failures and OOM while building traces | `char[]` in the runtime; T2b N/A for String candidates; `docker run -m`, `timeout -k` |
| `value.data` in traces is a Java literal (`-3L`) | Decode `value.binary` |
| JBMC's declaration steps put garbage values on the `in_*` locals before the real assignment | Take the last assignment that has a `sourceLocation` |
| Assert message missing from the property description | Map by `sourceLocation.line` or by assertion ordinal |
| Contradictory assumptions give a vacuous PROVED | Mandatory reach run (`assert false`) |
| An unknown option prints help, not JSON (exit 64) | Treat any exit code other than 0 or 10, or unparsable JSON, as TOOL_ERROR |
| A runaway jbmc made the whole WSL VM unresponsive for about 15 min | Run every jbmc under `docker run -m <cap> --memory-swap <cap>` and `timeout -k 10 <T>` |

No extra tool is needed in the image. Bitwuzla or CVC5 are not installed, but the SMT path crashes
anyway (§7), so nothing is missing.

## 9. Go / No-go

**GO, with a narrowed scope**, for "JBMC as the Java T2b checker". It works when the code under
check is integer-only (the `long`-backed runtime, `char[]` for PIC X, and no JDK calls apart from a
validated whitelist) **and** the arithmetic is add, subtract, move or OCCURS loops. For units with
variable×variable multiply or divide it is **NO-GO as a prover**: the proof timed out at 900 s.
There it is used as a bug finder only.

* Java 17 class files load.
* The PROVED / COUNTEREXAMPLE / BOUND_INSUFFICIENT / TOOL_ERROR outcomes are unambiguous from the
  exit code plus `cProverStatus` plus the property ids.
* Counterexamples are found in seconds, extract cleanly, and replay concretely.
* Vacuity is detectable.

**The limits that must shape the design:**

1. **Proofs succeed only for add/subtract/move/OCCURS-style code.** These took 16–90 s per small
   paragraph, growing with each `/ %` and each loop iteration.
   * Equivalence proofs of **MULTIPLY / DIVIDE / COMPUTE with `*` or `/` between two variables did
     not finish in 900 s**.
   * For those units T2b is effectively a fast bug finder (CEX in about 6 s) and returns
     INCONCLUSIVE on timeout. It is not a proof.
   * Budget about 120 s per unit. Report a timeout as INCONCLUSIVE, not FAIL.
   * T1/T3 have to carry mul/div units.
2. LLM code that uses `BigDecimal`, `String`/`StringBuilder`, `System.arraycopy` or other JDK APIs
   is not checkable. The pre-scan must route it to `NOT_APPLICABLE`. Because most LLM output uses
   BigDecimal, T2b eligibility will be low unless the prompt asks for the runtime library.
3. A COUNTEREXAMPLE is reported as FAIL only after concrete replay confirms it.

## 10. Recommended verifier integration

**Compile:**

```bash
javac --release 8 -g -cp /usr/lib/cprover-api.jar:<runtime.jar> -d build <harness+ref+candidate sources>
```

**Pre-scan.** Run `javap -c -p` on the candidate classes. If they contain `invokedynamic`, or
`invoke*` into `java/` outside `java/lang/Object`, `java/lang/String`, `java/lang/StringBuilder`
and the whitelist, mark T2b `NOT_APPLICABLE` with that reason.

**Run** (inside the container with a memory cap; the bound K must cover the largest OCCURS or
PERFORM loop + 1):

```bash
timeout -k 10 120 jbmc <pkg>.T2bHarness --function <pkg>.T2bHarness.check \
  -cp build:/usr/lib/cprover-api.jar[:jdk-whitelist] \
  --unwind K --unwinding-assertions --sat-solver cadical \
  --java-assume-inputs-non-null --json-ui --trace > eq.json
timeout -k 10 60 jbmc <pkg>.T2bHarness --function <pkg>.T2bHarness.reach  <same flags> > reach.json
```

**Verdict:**

| eq.json | reach.json | T2b status |
|---|---|---|
| PROVED | COUNTEREXAMPLE on the REACH assert | **PASS** ("bounded proof over declared PIC domains, unwind K") |
| PROVED | PROVED | **ERROR** "vacuous harness" |
| COUNTEREXAMPLE, and replay reproduces the mismatch | any | **FAIL** with the field (from the line map), the inputs and the replayed values. Feeds the diagnosis stage. |
| COUNTEREXAMPLE, and replay does not reproduce | any | **INCONCLUSIVE** "spurious (unmodelled library call?)" |
| BOUND_INSUFFICIENT | any | **INCONCLUSIVE** "unwind bound K insufficient" (optionally retry with 2K) |
| TOOL_ERROR or timeout (exit 124/137) | any | **ERROR** / **INCONCLUSIVE** (timeout), with the ERROR messages attached |

**Harness template** (as generated per paragraph; see `Harness.java`):

```java
public final class T2bHarness {
  static long pic(int digits, boolean signed) {           // one per numeric input field
    long v = CProver.nondetLong(); long lim = Rt.pow10(digits);
    CProver.assume(v < lim); CProver.assume(signed ? v > -lim : v >= 0); return v; }
  static char picX() { char c = CProver.nondetChar(); CProver.assume(c >= ' ' && c <= '~'); return c; }

  public static void check() {
    long in_WS_A = pic(7, true);  /* ... one in_<field> local per field read by the unit ... */
    Ref ref = new Ref();  Cand cand = new Cand();         // identical initial state
    ref.wsA.unscaled = in_WS_A;   cand.setWsA(in_WS_A);   // (adapter for candidate's field layout)
    ref.para();  cand.para();
    assert ref.wsA.unscaled == cand.getWsA();             // one assert per field; generator records line->field
    /* ... */
  }
  public static void reach() { /* identical body up to and including both calls */ assert false; }
}
```

**Parsing:** use `parse_jbmc.py`.

* Verdict from the exit code, `cProverStatus` and the FAILURE property ids, with `.unwind.` meaning
  the bound was too small.
* Inputs: the last `in_*` assignment that has a `sourceLocation` in the failing property's trace,
  decoded from `value.binary`.
