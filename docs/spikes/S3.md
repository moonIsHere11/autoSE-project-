# S3 — OpenJML ESC as the Java T3 checker

Spike date: 2026-11-06 · time box ≈2 h · everything below was run inside
`cobol-verifier-toolchain:0.1.0` on Docker-in-WSL2 (no image changes). Sources, scripts and raw
outputs are in [`s3/`](s3/):

* `s3/openjml-linux` — the launcher wrapper (the one artefact the verifier should ship);
* `s3/src/*.java` — toys: `Decimal`, `Account`, `Status`, `Loops`, `LoopEntry`, `Calls`, `Hard`,
  `Big`, `J17`, `Bad`;
* `s3/run.sh <File.java> [opts]` (one file in the container), `s3/all.sh`, `s3/provers.sh`,
  `s3/ce.sh`, `s3/timing.sh`, `s3/final.sh`, `s3/last.sh`, `s3/recommended.sh`, `s3/inspect.sh`,
  `s3/help.sh`, `s3/dock.sh`;
* `s3/out/*.txt` — raw outputs quoted below (`help.txt` is the full `--help`).

Run from WSL at the repo root, e.g. `bash docs/spikes/s3/run.sh Decimal.java -source 17 -Xlint:-options --progress`.

## Goal

Find out whether OpenJML's extended static checker can serve as tier T3 for Java: insert JML
contracts generated from the COBOL side into a copy of the LLM's Java and prove them. Concretely
(spec item S3): a working ESC command at Java 17 level, solver choice, the T3 idioms
(long-backed decimal truncation, frames, 88-level predicates, loops), the output format and exit
codes so results can be classified mechanically, timing/timeouts, and `BigDecimal` support.

## Workaround for the WSL-detection problem

**Cause.** `/opt/openjml/setup-vars` (sourced by the `openjml` launcher) does

```bash
if [ -n "$(grep -si microsoft /proc/version 2>/dev/null)" ]; then EXE=".exe" ; else EXE="" ; fi
...
if [ -n "$EXE" ]; then JSMTLIB_JAR=$(wslpath -w "$JSMTLIB_JAR"); fi
```

A container on Docker-in-WSL2 shares the WSL kernel (`/proc/version` = `Linux version
6.18.54.1-microsoft-standard-WSL2 …`), so the script believes it is on WSL, calls `wslpath`
and runs `javac.exe`. It is not just a warning — the stock launcher does **not run at all**:

```
$ openjml --version
/opt/openjml/setup-vars: line 25: wslpath: command not found
/usr/local/bin/openjml: line 32: /opt/openjml/jdk/bin/javac.exe: No such file or directory
```

(`os-name.sh` has the same probe and would answer `windows`; that only matters for solver-name
overrides, see `--os-name` below.)

**Fix (no image change).** Do what the launcher does for a Linux release, minus the probe: run the
bundled `javac` with jSMTLIB patched into `jdk.compiler`. Shipped as
[`s3/openjml-linux`](s3/openjml-linux):

```bash
#!/usr/bin/env bash
set -euo pipefail
INSTALL="${OPENJML_INSTALL:-/opt/openjml}"
export OPENJML_INSTALL="$INSTALL"
export SMT_SOLVER_DIR="${SMT_SOLVER_DIR:-$INSTALL/Solvers-linux}"
export OJ="${OJ-}"   # same "issue #876" hack as the original launcher
exec "$INSTALL/jdk/bin/javac" "-J--patch-module=jdk.compiler=$INSTALL/libs/jSMTLIB.jar" "$@"
```

```
$ bash ./openjml-linux --version
openjml 21.0.28
```

Wrapper-less one-liner (equivalent; the verifier can build this argv directly):

```bash
docker run --rm -v "$WORK:/w" -w /w \
  -e OPENJML_INSTALL=/opt/openjml -e SMT_SOLVER_DIR=/opt/openjml/Solvers-linux \
  cobol-verifier-toolchain:0.1.0 \
  /opt/openjml/jdk/bin/javac -J--patch-module=jdk.compiler=/opt/openjml/libs/jSMTLIB.jar \
  --esc -source 17 -Xlint:-options --os-name=linux --progress … File.java
```

Run in [`s3/final.sh`](s3/final.sh): with the two `-e` variables → `exit=0` (`Account.deposit`
verified). **`OPENJML_INSTALL` is required** — without it:

```
error: Could not find the internal system specifications: /w/null/specs
warning: Could not locate the internal specifications files - you may need to add the jmlspecs.jar explicitly on the command-line using --specs-path.
```

`SMT_SOLVER_DIR` is where the bundled solvers are looked up (proved by pointing it at `/tmp`:
`error: Specified executable does not exist: "/tmp/z3-5.1.0"` for the default prover,
`"/tmp/z3-4.16.0"` with `--prover=z3`).

## Commands

ESC on one file (what [`s3/run.sh`](s3/run.sh) runs):

```bash
bash ./openjml-linux --esc --os-name=linux -source 17 -Xlint:-options \
     --progress --show-summary [--timeout=N] [--method=NAME] [--check-feasibility=precondition] \
     src/File.java
```

* **Java 17 level: use `-source 17`, not `--release 17`.** `--release 17` makes javac take the
  platform classes from `ct.sym`, which breaks OpenJML's patched `java.base` specs — hundreds of
  errors, starting with
  `src/Decimal.java:1: error: package org.jmlspecs.lang does not exist` and
  `(package org.jmlspecs.annotation is declared in the unnamed module, but module java.base does not read it)`.
  `-source 17` works; it prints `warning: [options] system modules path not set in conjunction with -source 17`,
  silenced by `-Xlint:-options`. `-source 17` correctly accepted `var`, switch expressions and a
  `record` ([`J17.java`](s3/src/J17.java): all 4 methods `no warnings`). Caveat: with `-source 17`
  the JDK 21 class library is visible, so a JDK-21-only API call would not be flagged here — T0
  (JDK 17 `javac`) already catches that.
* `--os-name=linux` stops the Java side using `.windows` solver overrides (harmless for z3; kept for safety).
* `--progress` (verboseness 2) is what gives one machine-parsable status line per method; plain
  `--esc` only prints warnings.
* Solver selection (all on [`Decimal.java`](s3/src/Decimal.java): expected 3 valid + 2 invalid;
  [`s3/out/provers.txt`](s3/out/provers.txt)):

  | Option | Result |
  |---|---|
  | _(none)_ | prover `z3-5.1.0` (bundled), 3 valid / 2 invalid ✔ |
  | `--prover=z3` | bundled z3 (`jsmtlib.properties`: `org.smtlib.solver_z3.exec=z3-4.16.0`), ✔ |
  | `--prover=z3 --exec=/usr/bin/z3` (apt 4.8.12) | ✔ |
  | `--prover=z3 --exec=/opt/pyenv/bin/z3` (pip 5.3.3) | ✔ |
  | `--prover=z3 --exec=/opt/openjml/Solvers-linux/z3-4.12.6` | ✔ |
  | `--prover=cvc5` (bundled 1.3.2) | ✔, but `addTruncBuggy` 5.17 s vs ≈1.3–1.6 s with z3 |
  | `--prover=yices2` | **ERROR** every method: `(error "quantifiers are not allowed in logic ALL")` |
  | `--prover=z3_4_3` | **ERROR**: `Specified executable does not exist: "/opt/openjml/Solvers-linux/z3_4_3"` |
  | `--prover=z3 --exec=/nonexistent/z3` | `error: Specified executable does not exist: "/nonexistent/z3"`, exit 1 |

  Recommendation: pin `--prover=z3 --exec=/opt/openjml/Solvers-linux/z3-4.16.0` (or leave the default
  z3-5.1.0) — use OpenJML's own tested binary, not the pip/apt ones.

## Findings (toy examples)

All runs: `--esc -source 17 -Xlint:-options --progress --show-summary`, default prover.

### 1. `long`-backed decimal helper — [`Decimal.java`](s3/src/Decimal.java)

`ADD A TO B GIVING X` with `X PIC S9(5)` (sign kept, high-order digits truncated). Two forms of
contract: generic `\result == (a + b) % mod` with `mod` a parameter (non-linear), and a fixed-width
form for PIC S9(5) written without `%`. Correct versions verify, both planted bugs are reported as
postcondition failures:

```
Completed proof of Decimal.addTrunc(long,long,long) with prover z3-5.1.0 - no warnings [0.99 secs]
Completed proof of Decimal.addTrunc5(long,long) with prover z3-5.1.0 - no warnings [1.14 secs]
Starting proof of Decimal.addTrunc5Buggy(long,long) with prover z3-5.1.0
Method assertions are INVALID
src/Decimal.java:37: verify: The prover cannot establish an assertion (Postcondition: src/Decimal.java:31:) in method addTrunc5Buggy
        return s;
        ^
src/Decimal.java:31: verify: Associated declaration: src/Decimal.java:37:
    //@ ensures -100_000 < \result && \result < 100_000;
        ^
Completed proof of Decimal.addTrunc5Buggy(long,long) with prover z3-5.1.0 - with warnings [1.64 secs]
...
src/Decimal.java:47: verify: The prover cannot establish an assertion (Postcondition: src/Decimal.java:43:) in method addTruncBuggy
```

Default arithmetic modes are what T3 wants: `--code-math=safe` (Java code is checked for `long`
overflow — reported as `(ArithmeticOperationRange) … overflow in long sum`) and
`--spec-math=bigint` (contracts are mathematical integers, so `a + b` in an `ensures` cannot overflow).

additionally writes `audit`:

```

### 3. 88-level conditions as named predicates — [`Status.java`](s3/src/Status.java)

`88 STATUS-OK VALUE 'A' 'B'`, `88 STATUS-END VALUE 'Z'`. Four encodings tried, one method each:

| Encoding | Result |
|---|---|
| (a) `/*@ public static model pure boolean okBodyOnly(char s) { return s=='A'\|\|s=='B'; } @*/` — body only | **does not work**: correct code reported `Postcondition` failure. ESC is modular and does not unfold a method body; it only uses the method's contract. |
| (b) model method with a contract and no body: `/*@ public normal_behavior ensures \result == (s=='A'\|\|s=='B'); public static model pure boolean statusOk88(char s); @*/` | **works** (`setStatusB … no warnings`); prints `Skipping proof of Status.statusOk88(char) (because the method has no body)` — harmless |
| (c) model field `//@ public model boolean isOk;` + `//@ public represents isOk = (status=='A'\|\|status=='B');` | **works**, but the field must be declared `public char status; //@ in isOk;` otherwise a type error: `Because 'isOk' reads 'status' in a represents clause, 'status' must be 'in' the model field 'isOk'` |
| (d) Java helper `public static /*@ pure @*/ boolean isOkCode(char c)` with `//@ ensures \result == (…)` | **works** |

Bug "forgot `VALUE 'B'`" is caught:
`src/Status.java:65: verify: The prover cannot establish an assertion (Postcondition: src/Status.java:63:) in method setStatusBuggy` (`ensures statusOk88(in) ==> status == in;`).

**T3 should emit (b)**: spec-only, injectable without touching the LLM's Java, no `in` clauses needed.

### 4. Loops — [`Loops.java`](s3/src/Loops.java), [`LoopEntry.java`](s3/src/LoopEntry.java)

`PERFORM VARYING I FROM 1 BY 1 UNTIL I > N ADD I TO TOTAL`. With
`//@ maintaining … s == (long)(i-1)*i/2;` + `//@ decreases n - i + 1;` it verifies
(`sumTo … no warnings [1.06 secs]`; `loop_invariant` is accepted as a synonym of `maintaining`,
`fiveTimes … no warnings`). Variants:

* **No invariant** (`sumToNoInv`): OpenJML does *not* say "missing invariant". The loop body is
  havocked (all loop-modified locals become arbitrary), so you get ordinary-looking failures:

  ```
  src/Loops.java:24: verify: The prover cannot establish an assertion (ArithmeticOperationRange) in method sumToNoInv: overflow in long sum
  src/Loops.java:24: verify: The prover cannot establish an assertion (ArithmeticOperationRange) in method sumToNoInv: underflow in long sum
  src/Loops.java:26: verify: The prover cannot establish an assertion (Postcondition: src/Loops.java:20:) in method sumToNoInv
  Completed proof of Loops.sumToNoInv(int) with prover z3-5.1.0 - with warnings [1.53 secs]
  ```

  These lines are **indistinguishable** from a real bug. The distinction has to come from the
  source, not the output: see the classification rules below.
* **Wrong (non-inductive) invariant** (`sumToBadInv`): `(LoopInvariant)` plus a consequent
  `Postcondition` failure:

  ```
  src/Loops.java:40: verify: The prover cannot establish an assertion (Postcondition: src/Loops.java:31:) in method sumToBadInv
  src/Loops.java:35: verify: The prover cannot establish an assertion (LoopInvariant) in method sumToBadInv
          //@ maintaining s == (long) i * i / 2;
  ```
* **Wrong variant** (`sumToBadVariant`, `decreases i;`):
  `src/Loops.java:50: verify: The prover cannot establish an assertion (LoopDecreases) in method sumToBadVariant`
* **Invariant false on entry** (`fiveTimesBadEntry`, `s == 5L * i + 1` with `s = 0, i = 0`):
  `src/LoopEntry.java:8: verify: The prover cannot establish an assertion (LoopInvariantBeforeLoop) in method fiveTimesBadEntry`
* **No invariant, postcondition independent of the loop** (`countNoInv`, returns `n`, loop only
  increments a local `k`): the postcondition *is* proved (havoc is a sound over-approximation), but
  the havocked `k` produces
  `(ArithmeticOperationRange) in method countNoInv: overflow in int sum` at `k++` — again a
  spurious-looking warning caused only by the missing invariant.
* `decreases` is optional; without it only partial correctness is proved (no termination check).

## Output format and exit codes

Per-method status line (only with `--progress`):

```
Completed proof of <Class>.<method>(<param types>) with prover <prover> - <STATUS> [<secs> secs]
```

| Situation | `<STATUS>` | Detail lines (`verify:` / `error:`) | Summary bucket | Exit code |
|---|---|---|---|---|
| verified | `no warnings` | — (`Method assertions are validated`) | `Valid` | 0 if every method verified |
| postcondition failure | `with warnings` | `verify: The prover cannot establish an assertion (Postcondition: F:L:) in method M` + `verify: Associated declaration: …` | `Invalid` | 6 |
| frame violation | `with warnings` | `… (Assignable: F:L:) in method M: <field>` | `Invalid` | 6 |
| loop invariant / variant | `with warnings` | `… (LoopInvariant) …`, `… (LoopInvariantBeforeLoop) …`, `… (LoopDecreases) …` | `Invalid` | 6 |
| runtime-safety / library check | `with warnings` | seen: `… (ArithmeticOperationRange) … overflow in long sum` / `underflow in long sum` / `overflow in int sum`; `… (UndefinedCalledMethodPrecondition: /opt/openjml/specs/…)`. Not exercised here (OpenJML's other implicit checks, e.g. division by zero, null dereference, array index) — expect the same line shape with other keys | `Invalid` | 6 |
| solver timeout / unknown | **`UNKNOWN`** | `verify: Validity is unknown - no model available method Hard.fermat3 -  (possible timeout): (error "line 590 column 18: model is not available")` | **`Invalid`** (not `Timeout`!) | 6 |
| contradictory precondition (only with `--check-feasibility=precondition`) | `INFEASIBLE` | `verify: Invariants+Preconditions appear to be contradictory in method J17.vacuous(long)` | `Infeasible` | 6 |
| prover failure | `ERROR` | `error: An error while executing a proof script for …` / `error: No executable is known for prover …` | `Error` | 1 |
| JML/Java parse or type error | _(no proof runs)_ | `src/Bad.java:3: error: illegal start of expression` … `Operation not performed because of parse or type errors` | — | 1 |
| bad command line (e.g. file not found) | — | `error: file not found: src/.java` + usage | — | 2 |
| method has no body (model method) | `Skipping proof of … (because the method has no body)` | — | `Skipped` | — |

Notes:
* Exit code **6** = "verification warnings found" (`--verify-exit`, default 6; `--verify-exit=0`
  turns it into 0 — don't). It does not separate FAIL from UNKNOWN; parse the per-method lines.
* The trailing `N verification failures` counts every `verify:` line including
  `Associated declaration` lines — don't use it as a method count.
* With a timeout and a definite warning in the same method, the status is `with warnings` (seen on
  the first `Hard` run, [`s3/out/Hard.txt`](s3/out/Hard.txt), when the bounds were still
  `2_000_000` so `a*a*a + b*b*b` could really overflow: `ArithmeticOperationRange` +
  `Validity is unknown`, status `with warnings`; the file now uses `1_000_000`) — so look at all lines,
  not only the status word.
* **Vacuity**: a contradictory `requires` verifies silently by default
  (`J17.vacuous … no warnings`). T3 must pass `--check-feasibility=precondition`.

### Counterexamples

`--counterexample` prints the raw SMT model after the warning
([`s3/out/ce_counterexample.txt`](s3/out/ce_counterexample.txt)), for `addTrunc5Buggy`:

```
COUNTEREXAMPLE
...
b_1840_1840___9 = (- 1)
a_0_0___4 = 0
b_0_0___5 = 0
s_1858_1858___12 = 0
`result_1812_1812___10 = 0

i.e. `a = -99999, b = -1` (the parameter is the `<name>_<pos>_<pos>___<n>` entry with non-zero
position; the `_0_0_` copies are noise). `--trace` gives a readable execution path, and

## Timing

Per-method times are the `[… secs]` on the `Completed proof` lines (they are per method, not
cumulative: they add up to the `Completed proving methods in <Class>` total).

| What | Time |
|---|---|
| `docker run --rm IMG true` | 0.66 s |
| docker + `openjml-linux --version` (JVM start) | 2.3 s |
| docker + ESC start-up with no method to prove (`--method=doesNotExist`) | 7.3 s / 11.1 s (two runs, different load) |
| docker + `--check` only (parse + type-check JML) | 8.0 s |
| simple valid method (toys) | 0.4–1.5 s; first method of a run ≈0.7–0.9 s extra for solver start |
| failing method (model + counterexample extraction) | 1.3–2.3 s |
| `BigDecimal` methods (big library specs) | 2.4–5.1 s |
| `Decimal.java`, 5 methods | 6.3 s proving, 9.2 s wall |
| recommended command, 4 files / 22 methods in one JVM ([`s3/out/recommended.txt`](s3/out/recommended.txt)) | 25.8 s proving, 36.9 s wall |
| `cvc5` on non-linear `addTruncBuggy` | 5.17 s (z3: 1.3–1.6 s) |

**Timeouts.** `--timeout=N` limits "any individual proof attempt" in seconds — in practice per
method. `Hard.fermat3` (non-linear `a³+b³ != c³`, can't be decided) took 6.10 s with
`--timeout=5` and 21.23 s with `--timeout=20`, reporting `- UNKNOWN` both times. The default is
**infinite**, so always pass `--timeout`, and also put an outer wall-clock limit (`timeout(1)`)
around the container: one run of `LoopEntry.countNoInv` with no `--timeout` took **702.18 s**
during a period when the WSL VM was stalled by other jobs (the same method takes 1.54 s when
re-run normally) — nothing inside OpenJML would have stopped it.

Rule of thumb for budgeting T3 per program: ≈8–11 s fixed + ≈1–2 s per method, plus up to
`--timeout` for each hard method. Run **one OpenJML process per program** (all paragraph methods
in one call, `--method=` to select), not one per method, to pay the start-up once.

## `java.math.BigDecimal`

Poor, as expected ([`Big.java`](s3/src/Big.java), [`s3/out/Big.txt`](s3/out/Big.txt)). Specs exist
(`/opt/openjml/specs/java/math/BigDecimal.jml`) but only at nullity/shape level:

* `ensures \result != null` for `a.add(b)` — verifies.
* `addZero` (`ensures \result.compareTo(a) == 0` for `a.add(BigDecimal.ZERO)`), `addComm`
  (`\result.equals(b.add(a))`), `round2` (`\result.scale() == 2` after `setScale(2, HALF_UP)`) —
  all **correct but reported INVALID**, e.g.
  `(UndefinedCalledMethodPrecondition: /opt/openjml/specs/java/lang/Comparable.jml:78:)`,
  `(Postcondition: src/Big.java:30:)`, plus warnings
  `A non-pure method is being called where it is not permitted: java.math.BigDecimal.add(java.math.BigDecimal)`.
* The buggy `subtract` version fails too, but for the same irrelevant reasons.

So OpenJML cannot prove value-level facts about `BigDecimal` arithmetic. Methods whose relevant
state is `BigDecimal` → T3 `NOT_APPLICABLE` ("BigDecimal not supported by ESC"), consistent with the
`long`-backed decimal convention.

## Calls into helpers / the runtime library

[`Calls.java`](s3/src/Calls.java): the same `(a + b) % 100_000` contract, implemented by calling
a helper `trunc5…(a + b)`:

| Helper | Caller result |
|---|---|
| no JML contract (`trunc5NoSpec`) | **correct code reported as a FAIL**: `(Postcondition: src/Calls.java:17:) in method addViaNoSpec` |
| `//@ ensures \result == x % 100_000;` + `/*@ pure @*/` (`trunc5Spec`) | verified |
| `/*@ inline @*/` modifier, no contract (`trunc5Inline`) | verified (body substituted at the call site); prints `warning: Method trunc5Inline(long) has no assignable clause, so it is implicitly 'assignable \everything', making its caller likely impossible to verify` but proves anyway |

Consequence: a `Postcondition` warning is only trustworthy if every method the target calls has
a contract (or is `inline`). For calls into the `cobolrt` runtime library this means shipping JML
contracts for the runtime API (DESIGN.md risk row "OpenJML cannot handle the runtime library").
For helpers the LLM wrote inside the translated class, T3 can insert `/*@ inline @*/` (tested only on a one-line,
non-recursive helper) instead of inventing contracts for them.

## Problems

1. Stock `openjml` launcher is unusable on Docker-in-WSL2 (fixed by the wrapper, above).
2. `--release 17` is broken with OpenJML's specs; use `-source 17 -Xlint:-options`.
3. Missing loop invariants are not reported as such — must be detected from source.
4. Timeouts are counted as `Invalid` in the summary; only the per-method `UNKNOWN` status / the
   `Validity is unknown` line identifies them.
5. Vacuous preconditions pass silently unless `--check-feasibility=precondition`.
6. ESC is modular: model methods need contracts, not bodies; called helpers need contracts.
7. `BigDecimal` value reasoning is not supported.
8. Fixed start-up cost of ≈7–11 s per invocation (docker + JVM + OpenJML set-up, measured with
   no method to prove), so batch all methods of a program into one call.
9. Timings in this spike were measured while other spikes were loading the same WSL VM (load
   average up to ~80 at one point); treat them as upper bounds.

## Go / No-go

**GO** for "OpenJML ESC as the Java T3 checker", with these conditions:

* invoke it through the `openjml-linux` wrapper (or the equivalent argv with `OPENJML_INSTALL`
  and `SMT_SOLVER_DIR` set) — the stock launcher does not run in our container;
* `-source 17 -Xlint:-options`, never `--release 17`;
* always `--timeout` plus an outer wall-clock limit, and `--check-feasibility=precondition`;
* contracts in the shapes shown to work: `long` arithmetic with `requires` bounds, `assignable`
  frames, 88-levels as body-less `model pure` methods with a `normal_behavior ensures`, loop
  invariants via `maintaining`/`loop_invariant` + `decreases`;
* T3 is `NOT_APPLICABLE` for methods with un-invariant'd loops that don't verify, for
  `BigDecimal` state, and for calls to methods without contracts.

Everything T3 needs was demonstrated: correct versions of all four idioms verify, every planted bug
(sign truncation, frame write, missing 88 `VALUE`, bad invariant/variant) is reported as a
specific, parseable warning, run time is seconds per method, and output plus exit codes are
regular enough to classify mechanically. The real cost is not OpenJML; it is generating good
contracts and loop invariants and specifying callees.

## Recommended verifier integration

### Command (one process per program; verified in [`s3/recommended.sh`](s3/recommended.sh))

```bash
timeout --kill-after=10s "$T3_WALL" \
docker run --rm --network=none -v "$WORK:/w" -w /w cobol-verifier-toolchain:0.1.0 \
  bash /w/openjml-linux --esc --os-name=linux -source 17 -Xlint:-options \
    --progress --show-summary \
    --prover=z3 --exec=/opt/openjml/Solvers-linux/z3-4.16.0 \
    --timeout="$T3_PER_METHOD" --check-feasibility=precondition \
    [--method=para1,para2] \
    T3/Prog.java [other generated .java files]
```

(`openjml-linux` is copied into the work dir, or baked into the verifier's sandbox mount.
`--method` takes a comma-separated list of name patterns per `--help`; only a single simple
name was tried here. `--network=none` was part of the verified run.)
Suggested defaults: `T3_PER_METHOD=30`, `T3_WALL = 15 + n_methods × (T3_PER_METHOD + 5)` seconds.
For FAIL methods only, re-run once with `--method=<m> --trace --subexpressions --counterexample`
and attach the trace as the counterexample (keeps the main output simple to parse).

### Parsing

Split stdout+stderr into per-method blocks between
`Starting proof of <sig> with prover …` and

```
^Completed proof of (?P<sig>\S+\(.*\)) with prover \S+ - (?P<st>no warnings|with warnings|UNKNOWN|INFEASIBLE|ERROR) \[(?P<secs>[\d.]+) secs\]$
```

and collect, inside each block, the warning lines

```
^(?P<file>[^:]+):(?P<line>\d+): verify: The prover cannot establish an assertion \((?P<key>\w+)(?::[^)]*)?\) in method (?P<m>\w+)(?:: (?P<detail>.*))?$
^\S+: verify: Validity is unknown
^\S+: verify: Invariants\+Preconditions appear to be contradictory
```

ignoring `Associated declaration`, `Associated method exit`, `Precondition conjunct is false`
and `Feasibility check #… : OK` lines. Attribute warnings to the enclosing block (not to
`in method <name>`, which is ambiguous for overloads). Also scan globally for `^.*: error: ` and
`Operation not performed because of parse or type errors`.

### Classification (first matching rule wins, per target method)

Static facts computed by the verifier from the source before the run (tree-sitter):
`has_unannotated_loop(m)` = `m` contains a `for`/`while`/`do` with no `maintaining`/`loop_invariant`
directly before it; `calls_unspecified(m)` = `m` calls a method that has neither a JML contract
nor `inline` (excluding JDK methods with OpenJML specs that we whitelist).

| # | Condition | T3 status (reason) |
|---|---|---|
| 1 | outer `timeout` fired (exit 124/137) | `TIMEOUT` ("OpenJML wall-clock limit") |
| 2 | exit code ∉ {0, 6}, any `error:` line, `Operation not performed because of parse or type errors`, or block status `ERROR` | `ERROR` (quote the `error:` lines — usually a bug in our contract insertion) |
| 3 | no `Completed proof` line for a target method | `ERROR` ("method not proved / not found") |
| 4 | status `INFEASIBLE` | `ERROR` ("contradictory preconditions — vacuous contract"); never PASS |
| 5 | status `no warnings` | `PASS` (partial correctness if the loop has no `decreases`) |
| 6 | `has_unannotated_loop(m)` and any warning | `NOT_APPLICABLE` ("needs loop invariant"); list the warnings as hints |
| 7 | any key `LoopInvariant`, `LoopInvariantBeforeLoop`, `LoopDecreases` | `NOT_APPLICABLE` ("generated loop invariant/variant not provable") |
| 8 | `calls_unspecified(m)`, or a key `UndefinedCalledMethodPrecondition`, or a warning whose `Associated declaration` is under `/opt/openjml/specs/` | `NOT_APPLICABLE` ("callee/library without usable contract") |
| 9 | any warning with key `Postcondition`, `Assignable`, `ArithmeticOperationRange` (or another OpenJML implicit-check key) | `FAIL` (key, file:line, the `ensures`/`assignable` text, trace as counterexample) |
| 10 | status `UNKNOWN` / `Validity is unknown` and no rule-9 key | `TIMEOUT` ("solver timeout/unknown after N s") |
| 11 | anything else | `ERROR` ("unclassified ESC output") — keeps the zero-false-positive policy |

Do not use the exit code to distinguish FAIL from TIMEOUT (both 6), nor the `Summary:` counts
(timeouts are counted as `Invalid`). Suggested (not tried in this spike): before reporting a T3
`FAIL`, replay the counterexample inputs through T1; if COBOL and Java produce the same output on
them, downgrade to `NOT_APPLICABLE` ("ESC counterexample not confirmed") rather than emit a
possibly-false FAIL.

### Contract-generation rules learned

* Name 88-levels as body-less `model pure` methods with a `normal_behavior ensures \result == (…)`.
* Bound every numeric input with `requires` derived from its PIC (so `code-math=safe` overflow
  checks are meaningful and z3 stays in linear arithmetic where possible); prefer fixed-modulus
  postconditions (`10^n` literal) over a symbolic modulus.
* Give every non-target helper either a contract or `/*@ inline @*/`.
* Never use `BigDecimal` in T3; methods whose state is `BigDecimal` → `NOT_APPLICABLE`.
