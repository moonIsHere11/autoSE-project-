# Limitations (COBOL → Java verifier)

Everything here is reported by the verifier as NOT_APPLICABLE, ERROR or TIMEOUT with a reason.
None of it is ever reported as PASS. Status as of 6 Nov 2026.

## Scope of the COBOL side

* **Reference semantics are GnuCOBOL 3.2** (`cobc -x -std=default -fformat=fixed`). IBM Enterprise
  COBOL differences are not modelled.
* **Out of scope:** `EXEC SQL`, `EXEC CICS`, indexed/relative files, SORT/MERGE. Programs using them
  get T1+ NOT_APPLICABLE "uses <feature>". (`corpus/sqldemo` is an empty placeholder for such a test
  program; the self-test skips it.)
* CALL between programs is not supported.

## T1: differential testing

* T1 is **testing, not proof**: it covers the generated inputs (boundaries, rounding cases,
  literal-seeded values, pairwise and random; 265–408 cases per corpus program). A bug that shows
  only on inputs we never generate can slip through.
* Malformed numeric text on ACCEPT (`abc`, `1e3`) is not generated by default (DECISIONS D14).
* Programs that ACCEPT in a loop until a sentinel: the stdin length can't be known statically, so we
  use extra-line variants and literal-seeded terminators.

## T2a: exhaustive proof

* Applies only when the program's whole input space is below `exhaustive_limit` (20,000 cases).
  In the corpus that holds for 3 of 14 programs (DIVREM, TAXCALC, TEMPCONV).

## T2b: bounded model checking with JBMC (per paragraph)

* **Most paragraphs aren't eligible.** On the 14-program corpus (101 units), the reasons are:
  * **Paragraphs doing I/O** (ACCEPT/DISPLAY/READ/WRITE/OPEN/CLOSE): about half of all units. Their
    behaviour is covered at program level by T1/T2a.
  * **Division / exponentiation, and multiplication by a variable:** JBMC 6.8.0 found no verdict
    within 900 s (spike S2) because it has to prove two 64-bit multiplier/divider circuits
    equivalent. The `DIVIDE` statement is also outside the emitter's subset.
  * **Java `String`, `StringBuilder` or `BigDecimal` fields:** JBMC has no usable model for them (it
    silently stubs JDK methods, spike S2 §6.5). T2b needs `long`/`int` scaled numerics and `char[]`/`byte[]`.
  * **REDEFINES, COMP-5, reference modification, alphanumeric→numeric de-editing MOVE, GO TO,
    PERFORM THRU, intrinsic FUNCTIONs:** not in the reference emitter's subset (the exact construct is
    named in the reason).
  * **Two COBOL fields used by one paragraph that map to the same Java field.**
* **Memory:** each JBMC run is capped at 3 GB (WSL VM has 7 GB). Units with large alphanumeric
  state can be killed (`OUT_OF_MEMORY`). For example, the reachability (vacuity) run of the four
  empty `*-EXIT` paragraphs of MERGE2 was killed, so those units are ERROR even though the
  equivalence run itself passed.
* **Validation gate (b)** (reference vs COBOL model on random states) doesn't load OCCURS tables
  into the model, so units whose reference touches an OCCURS table are NOT_APPLICABLE.
* **Mutation sanity** needs at least 2 applicable mutants. For very small methods (e.g.
  `PAYROLL::SPLIT-HOURS`, `SET-RETURN`) the kill rate may be empty or computed on 1–2 mutants. The
  reachability check still runs.
* **Unit-level tiers (T1u/T2b/T3) judge a paragraph on *every* PIC-domain state**, not just states
  the program can reach. A translation that is correct as a whole program can still fail them. One
  example was PAYROLL `SPLIT-HOURS` storing a negative value into an unsigned field, a state the
  program never reaches. We fixed the translation, not the check.

## T3: contracts with OpenJML (per paragraph)

* No contract is generated for paragraphs with I/O, GO TO, PERFORM THRU, REDEFINES or COMP-5, or
  for fields held as `BigDecimal`/`String` numerics. Loops get range/frame contracts but no
  functional postcondition unless an invariant is supplied; missing invariants give NOT_APPLICABLE
  "needs loop invariant".
* **OpenJML 21.0.28 crash** (`AssertionError: isSameType DEFERRED`) on ordinary Java, such as a
  reference-typed `c ? a : b` passed as a method argument. Workaround: in the verification *copy*,
  the bodies of methods **not under check** are replaced by a `throw`. This is sound for modular
  ESC: callees are used through their specs, and a unit calling an uncontracted method is
  NOT_APPLICABLE anyway. If the crash comes from a unit method's own body, T3 still reports ERROR.
* An ESC warning without a concrete counterexample from T1u is NOT_APPLICABLE ("not confirmed"),
  never FAIL.

## Runtime library

* OpenJML ESC on `cobolrt.Num`/`Alnum` doesn't run yet: `runtimes/java/esc/run_esc.sh` copies the
  sources without their `cobolrt/` package directory, so `Round`/`Usage` can't be resolved (43
  errors in `runtimes/java/esc/esc.log`). The library is validated only by differential testing
  against GnuCOBOL (10,000 random cases, 0 mismatches).
* Numeric-edited PICTURE formatting is partial.

## Languages

* **Python and Go are deferred.** Their language packs, runtimes, tests and corpus translations stay
  in the repo, untouched, and weren't re-validated in this round. Python T2b/T3 (CrossHair) are
  labelled STUB; Go T2b/T3 are NOT_APPLICABLE by design.
